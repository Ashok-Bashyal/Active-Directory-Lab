# Project Overview

This project documents the design, implementation, and security monitoring of a virtualized Active Directory environment using VMware Workstation Pro, Windows Server 2022, Windows 10, Ubuntu Server, and Kali Linux.

The primary objective was to simulate a small enterprise network where I could configure Active Directory Domain Services, implement centralized security logging, generate controlled attack activity, and investigate suspicious events using Splunk Enterprise.

The environment consists of four virtual machines, each serving a different purpose. Windows Server 2022 acts as the Active Directory Domain Controller and DNS Server, Windows 10 represents a domain-joined workstation, Ubuntu Server hosts Splunk Enterprise, and Kali Linux serves as the security testing machine.

To establish endpoint visibility, I installed **Microsoft Sysmon with Olaf Hartong's modular configuration** and **Splunk Universal Forwarder** on both Windows machines. These tools collect Windows Security, System, Application, and Sysmon events and forward them to a centralized Splunk server.

After configuring the infrastructure, I performed a controlled **RDP password brute-force attack simulation** against the Windows 10 workstation using NetExec. I then investigated the resulting authentication events in Splunk, including Windows Event IDs 4625 and 4776.

I also used Atomic Red Team to simulate selected MITRE ATT&CK techniques and examine the endpoint telemetry generated by those tests.

The purpose of this project was to develop practical experience with Active Directory administration, endpoint monitoring, security event collection, attack simulation, threat detection, and SIEM investigations.

## Project Objectives

- Build a virtualized enterprise network using VMware Workstation Pro.
- Install and configure Windows Server 2022 as an Active Directory Domain Controller.
- Configure DNS and create the `adlab.local` domain.
- Create and manage Active Directory Organizational Units and user accounts.
- Join a Windows 10 workstation to the Active Directory domain.
- Install and configure Splunk Enterprise on Ubuntu Server.
- Deploy Splunk Universal Forwarder on both Windows machines.
- Install Microsoft Sysmon using Olaf Hartong's configuration.
- Collect and centralize Windows Security and Sysmon events.
- Configure Kali Linux for authorized security testing.
- Simulate an RDP password brute-force attack using NetExec.
- Investigate authentication events using Splunk Search Processing Language.
- Simulate selected MITRE ATT&CK techniques using Atomic Red Team.
- Analyze security telemetry from multiple Windows endpoints.

> **Disclaimer:** All attack simulations and authentication tests documented in this project were performed within a personally controlled virtual HomeLab. The environment was created exclusively for cybersecurity education and authorized security testing.

# 1. Network Architecture

The first stage of the project involved designing a network architecture that would allow multiple virtual machines to communicate within a controlled environment.

The network consists of an Active Directory Domain Controller, a Windows 10 workstation, a centralized Splunk server, and a Kali Linux security testing machine.

All machines were connected through a VMware NAT network using the `192.168.10.0/24` subnet.

## 1.1 Network Diagram

![Active Directory SOC HomeLab Architecture](images/Lab%20Logical%20Diagram.jpeg)

The network diagram illustrates the relationship between the virtual machines and the centralized security monitoring infrastructure.

VMware provides the virtual networking environment, while Splunk Enterprise acts as the central destination for Windows security telemetry.

## 1.2 Network Configuration

| Device | Operating System | IP Address | Purpose |
|---|---|---|---|
| Domain Controller | Windows Server 2022 | `192.168.10.7` | Active Directory and DNS |
| Target Workstation | Windows 10 Pro | `192.168.10.100` | Domain-joined endpoint |
| Splunk Server | Ubuntu Server | `192.168.10.10` | SIEM and centralized logging |
| Attacker Machine | Kali Linux | `192.168.10.250` | Authorized security testing |
| NAT Gateway | VMware NAT | `192.168.10.2` | Default gateway |
| Host Adapter | VMware VMnet8 | `192.168.10.1` | Host-side network interface |

## 1.3 How the Environment Works

The Windows Server 2022 Domain Controller manages Active Directory accounts, authentication requests, and DNS resolution.

Windows 10 is joined to the domain and acts as the workstation monitored by Splunk.

Ubuntu Server hosts Splunk Enterprise and receives Windows event logs from both Windows machines through Splunk Universal Forwarder.

Kali Linux generates controlled security activity, including RDP authentication attempts against the Windows 10 workstation.

The resulting events are recorded by Windows and Sysmon, forwarded to Splunk, and analyzed using SPL.

## 4.3 Configuring the Splunk Server IP Address

The Splunk Enterprise server was assigned a static IP address.

A static IP address is important because the Windows endpoints use Splunk Universal Forwarder to send security logs to a known destination.

### Network Configuration

```text id="uc9bdu"
IP Address      : 192.168.10.10
Subnet Mask     : 255.255.255.0
Default Gateway : 192.168.10.2
DNS Server      : 8.8.8.8
```

### Step 1 — Open the Netplan Configuration

On Ubuntu, I opened the Netplan configuration file:

```bash id="46iqy0"
sudo nano /etc/netplan/00-installer-config.yaml
```

**What this command does:** Opens the Ubuntu network configuration file in Nano so that the interface can be assigned a static IP address.

### Step 2 — Configure the Static IP Address

The Netplan configuration used the following settings:

```yaml id="pflwhy"
network:
  ethernets:
    ens33:
      dhcp4: no
      dhcp6: no
      addresses: [192.168.10.10/24]
      nameservers:
        addresses: [8.8.8.8]
      routes:
        - to: default
          via: 192.168.10.2
      match:
        macaddress: 00:0c:29:63:a3:f1
      set-name: ens33
  version: 2
```

![Splunk Server Netplan Configuration](images/splunk%20server%20network%20configuration.png)

### Configuration Explanation

| Setting | Purpose |
|---|---|
| `ens33` | Ubuntu network interface |
| `dhcp4: no` | Disables automatic IPv4 configuration |
| `dhcp6: no` | Disables automatic IPv6 configuration |
| `192.168.10.10/24` | Assigns the static address and subnet |
| `8.8.8.8` | Google Public DNS resolver |
| `to: default` | Configures the default route |
| `via: 192.168.10.2` | VMware NAT gateway |
| `match: macaddress` | Identifies the network interface |
| `set-name: ens33` | Sets the interface name |

> **Important:** The MAC address shown above belongs to the VM used in this lab. Other virtual machines will normally have different MAC addresses.

## 11.4 Perform an RDP Password Brute-Force Attack Simulation

After configuring Remote Desktop and preparing the password list, I performed the controlled brute-force simulation using NetExec.

The objective was to attempt multiple passwords against the `tsmith` domain account and investigate the resulting authentication activity.

### Execute the Brute-Force Simulation

I ran the following command:

```bash id="juyh9p"
nxc -t 1 --jitter 3 rdp 192.168.10.100 -d ADLAB -u tsmith -p passwords.txt
```

### Command Breakdown

| Parameter | Description |
|---|---|
| `nxc` | Launch NetExec |
| `-t 1` | Use one concurrent worker |
| `--jitter 3` | Add spacing between authentication attempts |
| `rdp` | Select Remote Desktop Protocol |
| `192.168.10.100` | Windows 10 target machine |
| `-d ADLAB` | Active Directory domain |
| `-u tsmith` | Lab account used for testing |
| `-p passwords.txt` | Use the prepared password list |

**What this command does:** Performs a controlled RDP password brute-force simulation by testing multiple passwords for the specified domain account against the Windows 10 target.

Repeated incorrect passwords can trigger account lockouts, so this type of testing should be performed only with authorization and appropriate test-account controls.

### Authentication Results

During the simulation, NetExec attempted multiple passwords.

# 12. Security Event Investigation with Splunk

After completing the RDP brute-force simulation, I continued investigating the Windows Security events collected by Splunk.

## What Is SPL?

**SPL (Search Processing Language)** is the query language used by Splunk to search, filter, analyze, and correlate machine-generated data.

SOC analysts use SPL to investigate suspicious authentication activity, identify unusual processes, review endpoint telemetry, and search for potential security threats.

---

## 12.1 Event ID 4625 — Failed Windows Logon

Event ID 4625 is generated when Windows records a failed logon attempt.

### SPL Query

```spl id="hxuskr"
index=endpoint source="WinEventLog:Security" EventCode=4625
| table _time host _raw
| sort -_time
```

### Query Explanation

| Component | Purpose |
|---|---|
| `index=endpoint` | Select the endpoint index |
| `source="WinEventLog:Security"` | Search Windows Security events |
| `EventCode=4625` | Filter failed logon events |
| `table` | Display selected fields |
| `sort -_time` | Sort newest events first |

### Important Windows Logon Fields

| Field | Description |
|---|---|
| Account Name | User involved in the event |
| Account Domain | Domain associated with the account |
| Logon Type | Type of authentication attempt |
| Source Network Address | Originating IP address, when available |
| Status | Authentication failure status |
| Sub Status | Additional failure information |

These fields provide information that can help determine the cause of authentication failures.

## 12.2 Event ID 4624 — Successful Windows Logon

Windows Event ID 4624 records successful logon activity.

```spl id="14tk4n"
index=endpoint source="WinEventLog:Security" EventCode=4624
| table _time host _raw
| sort -_time
```

### Important Logon Types

| Logon Type | Description |
|---|---|
| 2 | Interactive |
| 3 | Network |
| 5 | Service |
| 10 | RemoteInteractive |
| 11 | CachedInteractive |

**Why this matters:** A successful Windows logon event does not necessarily mean the user accessed the desktop.

Logon Type 10 is particularly relevant when investigating actual RDP remote-interactive logons.

## 12.3 Event ID 4776 — NTLM Credential Validation

**NTLM (New Technology LAN Manager)** is a Microsoft authentication protocol used to verify credentials in Windows environments.

NTLM credential validation is the process of checking whether the credentials supplied during authentication are valid.

During the brute-force simulation, the Domain Controller generated Event ID 4776 events involving the test account.

### Important NTLM Status Codes

| Error Code | Meaning |
|---|---|
| `0x0` | Credential validation succeeded |
| `0xC000006A` | Incorrect password |
| `0xC0000234` | Account locked out |

### Search for NTLM Events

```spl id="thbs0n"
index=endpoint host=ADDC01 source="WinEventLog:Security" EventCode=4776
| table _time host _raw
| sort -_time
```

**What this query does:** Retrieves NTLM credential validation events collected from the Domain Controller.

### Classify Authentication Results

```spl id="1s302b"
index=endpoint host=ADDC01 source="WinEventLog:Security" EventCode=4776 "tsmith"
| rex field=_raw "Error Code:\s+(?<AuthStatus>0x[0-9A-Fa-f]+)"
| eval Result=case(
    lower(AuthStatus)="0x0", "Success",
    lower(AuthStatus)="0xc000006a", "Incorrect Password",
    true(), "Other"
)
| stats count by Result
```

### Command Explanation

- `rex` extracts the NTLM error code from the raw event.
- `eval` creates a readable authentication result.
- `case` categorizes the event based on the status code.
- `stats` counts the events in each category.

This makes it easier to separate successful credential validations from incorrect-password attempts.

> **Important:** A successful Event ID 4776 confirms that the credentials were accepted during NTLM validation. It does not automatically prove that an interactive RDP desktop session was established.

## 12.4 Investigating Sysmon Events

After examining authentication events, I investigated the Sysmon telemetry collected from the Windows endpoints.

The Sysmon data was forwarded in XML format.

### Search for Sysmon Events

```spl id="22ub59"
index=endpoint source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
```

### Extract Sysmon Event IDs

Some Sysmon XML events did not expose `EventCode` as a normally extracted field.

I used the following SPL query to extract Event IDs from the XML.

```spl id="p5xg4l"

| rex field=_raw "<EventID[^>]*>(?<SysmonEventID>\d+)</EventID>"
| stats count by host SysmonEventID
| sort -count
```

**What this query does:** Extracts the Sysmon Event ID from the raw XML and counts the different event types generated by each Windows endpoint.

- Executed processes

- DNS queries
- Suspicious process access

These events can help analysts investigate activities that may not be fully represented by standard Windows Security logs alone.

# 14. SPL Threat Detection Queries

Splunk Search Processing Language allows analysts to search, filter, correlate, and summarize security events.

The following queries demonstrate how the collected Windows and Sysmon logs can be used for additional threat detection and investigation.

These are reusable investigation and detection-engineering examples. They are not all claims of scheduled alerts deployed during the original lab.

---

## Detection 1 — Failed Windows Logons

```spl id="ewnos1"
index=endpoint source="WinEventLog:Security" EventCode=4625
| stats count as FailedLogons by host
| sort -FailedLogons
```

**Purpose:** Counts failed Windows logon attempts by host.

This can help identify machines experiencing repeated authentication failures.

---


## Detection 2 — Sysmon Process Creation

```spl id="2tzxwq"
index=endpoint source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
| rex field=_raw "<EventID[^>]*>(?<SysmonEventID>\d+)</EventID>"
| where SysmonEventID="1"
| table _time host _raw
| sort -_time
```

**Purpose:** Investigates Sysmon Event ID 1 process creation events.

These events can provide details about executed programs and process activity.

---

## Detection 3 — Sysmon Event Distribution

```spl id="ux9u77"
index=endpoint source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
| rex field=_raw "<EventID[^>]*>(?<SysmonEventID>\d+)</EventID>"
| stats count by host SysmonEventID
| sort -count
```

**Purpose:** Displays the number of events collected for each Sysmon Event ID and Windows host.

This helps identify the types of endpoint telemetry being received.

---

## Detection 4 — Windows Authentication Timeline

```spl id="iyvr5j"
index=endpoint source="WinEventLog:Security"
(EventCode=4624 OR EventCode=4625 OR EventCode=4771 OR EventCode=4776 OR EventCode=4740)
| table _time host EventCode _raw
| sort -_time
```

**Purpose:** Displays authentication-related events in chronological order for investigation.

This can help correlate failed logons, successful logons, credential validation events, and account lockouts.

---

## Detection 5 — Investigate a Specific Account

```spl id="vjxxuu"
index=endpoint source="WinEventLog:Security" "tsmith"
| table _time host EventCode _raw
| sort -_time
```

**Purpose:** Retrieves Windows Security events associated with the specified lab account.

## Detection 6 — Verify Endpoint Log Collection


**Purpose:** Confirms which monitored hosts and event sources are sending data to Splunk Enterprise.

This is useful for validating monitoring coverage.
